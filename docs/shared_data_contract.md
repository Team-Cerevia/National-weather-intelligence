# SHARED DATA CONTRACT

## National Weather Intelligence Platform

**Version:** `1.0`

**Status:** ACTIVE

**Purpose:** Shared interface between Data Ingestion, Streaming, Intelligence, Database/API and Dashboard components.

---

# 1. Why This Contract Exists

Three different teams are developing different parts of the platform in parallel.

We cannot have:

```text
Teammate 1:
{
  "location": "Noida",
  "content": "heavy rain"
}
```

while another component expects:

```text
{
  "city": "Noida",
  "text": "heavy rain"
}
```

and another expects:

```text
{
  "latitude": ...,
  "longitude": ...,
  "description": ...
}
```

That creates integration problems.

Therefore, we define **one canonical weather-report representation**.

Everything entering the platform must eventually become:

```text
WeatherReport
```

---

# 2. The Core Principle

All source-specific data follows:

```text
                    EXTERNAL SOURCES

       IMD ───────────────┐
       Weather APIs ──────┤
       Social Media ──────┤
       News/Web ──────────┤
       Public Datasets ───┤
       Citizen Reports ───┤
       Synthetic ─────────┘
                            │
                            ▼
                     SOURCE ADAPTER
                            │
                            ▼
                     WeatherReport
                            │
                            ▼
                       EVENT STREAM
                            │
                            ▼
                       INTELLIGENCE
                            │
                            ▼
                         DATABASE
                            │
                            ▼
                        DASHBOARD
```

The source-specific format must **never leak into downstream components**.

---

# 3. Ownership

## Teammate 1 — Ingestion

Produces:

```text
WeatherReport
```

from:

* IMD
* weather APIs
* social media
* news/web
* public datasets
* citizen reports
* synthetic data

---

## Teammate 2 — Streaming

Transports:

```text
WeatherReport
```

through the event stream.

They must not modify the meaning/content of the report.

---

## Intelligence Team

Consumes:

```text
WeatherReport
```

and derives:

* weather event category
* location
* severity
* credibility
* misinformation indicators
* semantic duplicates
* incident clusters
* evidence relationships

---

## Database/API

Stores the canonical report and derived intelligence.

---

## Dashboard

Reads processed/aggregated data.

---

# 4. Canonical Object

The central object is:

```text
WeatherReport
```

Every incoming weather-related observation/report must be representable using this model.

# 6. Field Specification

## `report_id`

Type:

```text
string / UUID
```

Required:

```text
YES
```

Description:

Unique identifier generated by our platform.

Example:

```text
"rep_01J7WEATHER123"
```

This is NOT necessarily the original source ID.

```text
string
```

Required:

```text
YES
```

```text

open_meteo
x
news
citizen
dataset
synthetic
```

Purpose:

Identifies the specific source system.

# 8. `source_type`

Type:

```text
enum
```


# 9. `source_id`

Type:

```text
string | null
```

Required:

```text
NO
```

The identifier from the original source.

Examples:

```text
X post ID
IMD bulletin ID
news article ID
dataset row ID
citizen report ID
```

Example:

```text
"183729182739"
```

If unavailable:

```text
null
```

---

# 10. `timestamp`

Type:

```text
ISO-8601 datetime
```

Required:

```text
YES
```

Meaning:

**When the reported observation/event occurred or when the source says it occurred.**

Example:

```text
2026-09-04T10:42:00Z
```

This is the **event time**.

Do not replace it with ingestion time.

---

# 11. `received_at`

Type:

```text
ISO-8601 datetime | null
```

Required:

```text
NO
```

Meaning:

When our platform received/processed the report.

Example:

```text
timestamp:
2026-09-04T10:42:00Z

received_at:
2026-09-04T10:44:13Z
```

This distinction is important for delayed reports.

---

# 12. `text`

Type:

```text
string
```

Required:

```text
YES
```

Human-readable content associated with the report.

Social media:

```text
"Sector 62 mein bahut tez baarish ho rahi hai #Noida #IMD"
```

News:

```text
"Heavy rainfall causes waterlogging across..."
```

Citizen:

```text
"Water has entered houses near..."
```

Structured API:

A deterministic textual description may be generated.

Example:

```text
"Temperature 38.2°C, precipitation 4.2 mm, wind speed 18 km/h."
```

# 14. IMPORTANT: Location Confidence

The initial `WeatherReport` should represent **what the source actually gives us**.

Do NOT put NLP-inferred location into:

```text
city
state
latitude
longitude
```

unless the intelligence layer has actually inferred it.

Instead, intelligence can produce a derived object such as:

```text
LocationEvidence
```

later.

Example:

```text
Original report:

"bhai sec 62 mein road doob gayi"

Initial:

city = null
state = null

NLP later:

city = "Noida"
location_confidence = 0.91
location_source = "text_extraction"
```

This prevents source facts and AI inferences from being mixed.


# 17. `media_urls`

Type:

```text
array[string]
```

Default:

```text
[]
```

Contains image/video URLs associated with the report.

Example:

```json
[
  "https://example.com/image.jpg"
]
```

For the MVP, we store references.

We do NOT need to download and process every video/image.

---

# 18. `hashtags`

Type:

```text
array[string]
```

Default:

```text
[]
```

Example:

```json
[
  "#IMD",
  "#NoidaRains",
  "#Flood"
]
```

Preserve the original hashtag when possible.

---

# 19. `language`

Type:

```text
string | null
```

Examples:

```text
en
hi
hinglish
unknown
```

This field is useful for the NLP layer.

However:

**Ingestion may provide a source-declared language or simple detection.**

The intelligence layer can later perform better language identification.

---

# 20. `raw_payload`

Type:

```text
object | null
```

Purpose:

Preserve source-specific information.

Example:

```json
{
  "original_author": "user123",
  "engagement": 1042,
  "source_specific_field": "..."
}
```

This allows future reprocessing without fetching the original source again.

---

# 21. Security Rule for `raw_payload`

Do NOT put:

* API keys
* passwords
* access tokens
* private credentials
* unnecessary personal information

into `raw_payload`.

---

The intelligence layer can derive:

```text
event_category

confidence
location inference
credibility

incident_id

```

These should ideally be represented as **derived fields/objects**, rather than silently overwriting source information.

---

# 29. Source Truth vs AI Inference

This is a critical architectural rule.

Never confuse:

```text
WHAT THE SOURCE SAID
```

with:

```text
WHAT OUR MODEL THINKS
```

Example:

```text
SOURCE:

"Flooding reported in Sector 62"

MODEL:

event_category = flooding
confidence = 0.94
```

The original text must remain unchanged.

---

# 30. Event Envelope

When the report enters the stream, it should be wrapped in an event.

Example:

```json
{
  "event_id": "evt_001",
  "event_type": "weather.report.created",
  "created_at": "2026-09-04T11:02:00Z",
  "schema_version": "1.0",
  "data": {
    "report_id": "rep_social_001",
    "source": "x",
    "source_type": "social_media",
    "timestamp": "2026-09-04T10:42:00Z",
    "text": "Heavy rain in Noida #IMD"
  }
}
```

The event envelope belongs to the **streaming layer**.

The `data` object is the `WeatherReport`.

---

# 31. Important IDs

Do not confuse these:

```text
source_id
```

Original source identifier.

```text
report_id
```

Our canonical report identifier.

```text
event_id
```

Identifier for the streaming event.

Later:

```text
incident_id
```

Identifier for the real-world weather incident inferred by the intelligence layer.

Therefore:

```text
source_id
    ↓
report_id
    ↓
event_id
    ↓
incident_id
```

They are NOT interchangeable.

---

# 32. One Incident Can Have Many Reports

Example:

```text
                  INCIDENT
                "Noida flooding"
                      │
       ┌──────────────┼──────────────┐
       │              │              │
       ▼              ▼              ▼
    Social          Citizen         News
    report           report        article
       │              │              │
       ▼              ▼              ▼
    report_1        report_2       report_3
```

All three remain separate `WeatherReport`s.

The intelligence layer may later assign:

```text
incident_id = INC_001
```

to all three.

---

# 33. Duplicate Principle

There are two different concepts.

## Exact/source duplicate

Same source ID:

```text
source = x
source_id = 123
```

This can be handled by ingestion.

---

## Semantic duplicate

Different reports:

```text
"Sector 62 is flooded"
```

and:

```text
"Waterlogging reported around Sector 62"
```

These may represent the same incident.

This belongs to the intelligence layer.

---

# 34. Timestamp Rules

All timestamps must be ISO-8601.

Prefer UTC internally:

```text
2026-09-04T10:42:00Z
```

Never use ambiguous formats such as:

```text
04/09/26 10:42
```

because different systems may interpret them differently.

---

# 35. Nullability Rules

Missing information should be:

```text
null
```

not:

```text
"unknown"
```

unless `"unknown"` is semantically meaningful.

Bad:

```json
{
  "latitude": "N/A"
}
```

Good:

```json
{
  "latitude": null
}
```

For arrays:

```text
[]
```

is preferred.

Example:

```json
{
  "media_urls": []
}
```

---

# 36. No Silent Data Fabrication

If a source says:

```text
"Heavy rain in Noida"
```

but gives no coordinates:

DO NOT invent:

```text
28.5355, 77.3910
```

unless another legitimate system explicitly provides that mapping.

Data provenance matters more than completeness.

---

# 37. Validation

Every `WeatherReport` must pass schema validation before entering the stream.

Minimum validation:

```text
report_id exists
source exists
source_type valid
timestamp valid
text exists
latitude valid if present
longitude valid if present
schema_version exists
```

# 38. Pydantic Implementation

The canonical Python model should live in:

```text
contracts/weather_report.py
```

Example structure:

```python
from datetime import datetime
from pydantic import BaseModel, Field

class WeatherReport(BaseModel):
    report_id: str
    source: str
    source_type: str
    source_id: str | None = None

    timestamp: datetime
    received_at: datetime | None = None

    text: str

    latitude: float | None = Field(default=None, ge=-90, le=90)
    longitude: float | None = Field(default=None, ge=-180, le=180)

    city: str | None = None
    district: str | None = None
    state: str | None = None
    country: str | None = "India"

    event_category: str | None = None

    url: str | None = None
    media_urls: list[str] = []
    hashtags: list[str] = []

    language: str | None = None

    raw_payload: dict | None = None

    schema_version: str = "1.0"
```

Use the project's existing Pydantic conventions if they differ.

---

# 39. JSON Schema

Generate:

```text
contracts/weather_report.schema.json
```

from the Pydantic model.

This gives non-Python components a language-independent representation of the contract.

Pydantic supports schema generation and validation, making it suitable for maintaining a shared contract between independently developed components.

---

# 40. Versioning Rule

Do NOT casually change the schema.

If you want to:

```text
add an optional field
```

discuss it first.

If you want to:

```text
rename a field
remove a field
change a field's meaning
```

that is a breaking change.

Update:

```text
schema_version
```

accordingly.

---

```text

```

# 46. Final Contract

The entire team agrees:

> **`WeatherReport` is the canonical representation of an incoming weather-related observation/report.**

Teammate 1 produces it.

Teammate 2 transports it.

The intelligence layer interprets it.

The database stores it.

The dashboard visualizes the resulting information.

No component should need to understand the original source's proprietary structure after normalization.
